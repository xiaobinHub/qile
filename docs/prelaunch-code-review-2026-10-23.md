## R01 · P1 · 实际页面备份没有包含图片，无法跨孩子恢复

位置：[parent-ui/src/App.tsx:117](../parent-ui/src/App.tsx#L117)，关键数据来源为第 125 行；服务端正确的便携导出实现位于 [media_service.py:146](../media_service.py#L146)。

页面“设置 → 数据备份 → 导出备份”直接把 `runtime` 中的 `s.data` 下载为 JSON。OSS 改造后，普通读取只返回 `imageAssetId` 和临时生成的同源 `imageUrl`，该按钮没有调用 `/api/children/{id}/data/export` 去读回图片内容。

浏览器真实点击结果：下载文件中有 40 个私有文件引用、0 个 `imageData`，发往 `/data/export` 的请求为 0。将同类前端备份恢复到另一个可管理孩子时返回 404“图片不存在或不可访问。”。备份因此依赖来源孩子及其对象存储，不能作为可独立恢复的便携备份；来源孩子删除或换库后也不能据此恢复图片。

建议：按钮改为调用经权限校验的服务端导出接口；下载完成后再提示成功，任何图片无法读取时保留明确错误。新增“实际点击页面导出 → 新孩子恢复 → 图片字节一致”的浏览器测试。现有后端测试调用了正确接口，页面下载测试则只在同一孩子恢复，所以没有覆盖断点。

## R02 · P1 · 当前 Python 证书信任库命中已公开漏洞

位置：[requirements.txt:7](../requirements.txt#L7)、[object_storage.py:64](../object_storage.py#L64)。

对当前 `.venv` 的 36 个包执行安全审计，确认安装的 `certifi 2026.7.22` 命中 `PYSEC-2026-4320 / GHSA-6q48-6c7w-9gw2`。OSV 独立查询确认该告警未撤回，修复版本为 `2026.10.19`。漏洞涉及被攻陷中间 CA 密钥所对应的受信任根，具备相应密钥及网络位置的攻击者可能冒充 HTTPS 服务。

`oss2` 实际通过 `requests` 发起请求，当前 `requests` 默认使用这份 certifi 证书包。因此问题影响 OSS HTTPS 连接的信任判断。项目只固定了直接依赖，没有约束此传递依赖；对已有环境仅重装当前 requirements 不保证升级 certifi。

建议：升级至至少 `2026.10.19`，将安全下限纳入依赖约束/锁定，并在待发布环境重新安装、重新审计及验证 OSS。该结论是当前本机候选环境的已知依赖漏洞，不代表已发生中间人攻击，也未检查或修改独立生产虚拟环境。

参考：[官方安全公告](https://github.com/certifi/python-certifi/security/advisories/GHSA-6q48-6c7w-9gw2)、[OSV](https://osv.dev/vulnerability/PYSEC-2026-4320)。

## R03 · P2 · 合法导出的较大备份无法恢复

位置：[accounts_app.py:21](../accounts_app.py#L21)、[accounts_app.py:79](../accounts_app.py#L79)、[media_service.py:153](../media_service.py#L153)、[deploy/nginx.example.conf:13](../deploy/nginx.example.conf#L13)。

礼品逐件保存文件引用，没有限制全部图片的总大小。服务端便携导出会把每件礼品的图片重新嵌入 JSON，而普通请求体和 Nginx 模板均限制为 8 MiB。

隔离复现：40 件礼品均引用有效的 173,299 字节图片，服务端正常导出 9,254,365 字节 JSON（约 8.83 MiB），立即通过恢复接口提交该内容返回 HTTP 413“提交内容过大。”。礼品长期累积后会出现“可下载备份却不能恢复”，修复 R01 后实际页面也会遇到此问题。

建议：统一备份生成、上传、反向代理和恢复的容量契约，支持有明确上限的分阶段或压缩恢复；不要只提高前端限制。测试至少覆盖多张接近 180 KiB 的图片以及超过 8 MiB 的真实导出文件，确保保留修订号、原操作 ID 和原子提交保护。

## R04 · P2 · 暂存文件清理部分失败会留下“可关联但已丢失”的图片

位置：[media_migration.py:160](../media_migration.py#L160)、[media_migration.py:166](../media_migration.py#L166)，相关引用检查为 [media_service.py:104](../media_service.py#L104)。

清理在一个孩子级数据库事务中依次执行多个 OSS 物理删除，再将状态改为 deleted。如果前面的对象已删除，而后一个对象删除失败，整个数据库事务会回滚；OSS 的前一个删除无法回滚。

隔离故障注入：创建两个超过 24 小时的未关联暂存对象，第一个删除成功、第二个故意失败。结果第一个文件的数据库状态回到 staged；将该资产保存为礼品返回 200，但读取图片返回 503。上传状态和关联检查只检查数据库记录，无法发现这个不一致。

此复现没有删除任何已关联真实历史对象；风险发生在清理失败后再次使用旧暂存引用。当前清理是手动工具，尚未自动调度，但启用时必须处理该边界。

建议：先持久化“不可再关联/待删除”状态，再在数据库事务外删除对象，记录可重试的清理状态；任意一个对象失败不能让已删除文件恢复为 staged。补充多对象部分失败和状态提交失败的回归。

## R05 · P2 · 图片完整解码发生在认证之前

位置：[media_service.py:59](../media_service.py#L59)、[media_service.py:170](../media_service.py#L170)、[media_types.py:46](../media_types.py#L46)。

上传先执行 `inspect_image`，之后才在 begin 事务中验证登录、来源、CSRF、孩子权限。恢复接口也在认证前验证全部业务数据并解码所有内嵌图片。文件允许解码到 1,600 万像素，180 KiB 网络体积限制不能等价限制内存和 CPU 开销。

隔离复现：完全没有 Cookie 的上传请求最终返回 401，但进入过完整图片解码函数。该结果确认顺序问题；没有对开发或生产执行并发压力攻击。当前入口也没有应用层上传速率或并发限额，因此未登录请求可占用解码资源和同步请求线程。

建议：保留入口字节大小限制，先完成廉价的认证、来源、CSRF 和孩子权限检查，再进行图片解码；为上传及大备份恢复增加有界并发和限流。补充“未登录/错误来源/撤权请求不进入解码阶段”的测试。

## R06 · P2 · 按月重复任务的次数会少一次

位置：[business_operations.py:108](../business_operations.py#L108)、[business_operations.py:139](../business_operations.py#L139)，前端同样存在于 [parent-ui/src/domain/calendar.ts:115](../parent-ui/src/domain/calendar.ts#L115)。

纯函数复现：开始日期 `2026-10-20`、每月 1 日、共 3 次。实际只生成 `2026-11-01` 和 `2026-12-01`；应有第三次 `2027-01-01`。前后端实现都存在同一问题，仅对比旧实现的等值测试无法发现。

建议：起始日前的候选日不消耗次数，但查询范围 from 之前的有效发生仍须计入总次数。分别为前后端增加独立期望值测试，覆盖起始月跳过、查询中间月份、跨年、间隔和月末回落。
